## 2026-10-21 — контракты данных и Zod-схемы

**Задача:** описать серверные модели и правила входных данных до создания API.

**Что сделано с помощью ИИ:**

- описаны модели `Form`, `Page`, `Field`, `Submission`, `Answer`;
- зафиксированы статусы `draft` и `published`;
- создана discriminated union по семи типам полей;
- описаны отдельные config-схемы для текста, email, числа, одиночного и
  множественного выбора;
- добавлены схемы создания и изменения формы;
- добавлена схема отправки ответов;
- добавлены проверки диапазонов, уникальности option ID и уникальности ответа
  на поле внутри одной отправки.

**Архитектурное решение:** поля выбора в черновике могут временно иметь пустой
`options`. Наличие вариантов будет обязательным при публикации, чтобы UI мог
создать поле, а затем постепенно его настроить.

**Проверка:** typecheck и lint проходят; корректное поле нормализуется, а
перевёрнутый числовой диапазон, повторяющиеся option ID и повторный ответ на одно
поле отклоняются.

**Правка после ревью пользователя:** пользователь заметил предупреждение о том,
что `.finite()` устарел в Zod 4. Проверка локальных типов Zod подтвердила, что
`z.number()` уже отклоняет `NaN` и бесконечные значения. Лишние вызовы
`.finite()` удалены без изменения поведения схем; typecheck и lint повторно
пройдены.

**Уточнение модели:** `Submission` — одна завершённая отправка формы, а
`Answer` — значение одного поля внутри этой отправки. Одна форма содержит много
submissions, одна submission содержит много answers. Запись submission и всех
её answers должна выполняться в одной транзакции.
