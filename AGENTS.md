# AGENTS.md — Form Service (FutureToday)

## 1. Контекст проекта

Проект — тестовое задание на позицию Junior Web Developer (AI-assisted) в FutureToday.

Разрабатываем автономный сервис создания и заполнения форм:

- Менеджер создаёт, редактирует и публикует формы через `/admin`.
- Каждая опубликованная форма доступна по уникальной ссылке.
- Студенты заполняют формы и отправляют ответы.
- Менеджер просматривает полученные заявки.

Приоритет — полностью работающее, понятное и проверяемое MVP.

## 2. Технологии

- Frontend: React, TypeScript, Vite, React Router, SCSS Modules.
- Backend: Node.js >= 20, TypeScript, Express.
- Валидация: Zod.
- База данных: SQLite через `better-sqlite3`, без ORM.
- Данные хранятся локально.

Не добавляй новые библиотеки без обоснованной необходимости. Предпочитай уже установленные инструменты.

## 4. Правила TypeScript

1. Используй строгую типизацию.
2. Предпочитай `type`, а не `interface`.
3. Не используй `any`, если можно описать конкретный тип или `unknown`.
4. Для полей разных типов используй discriminated union.
5. Не дублируй типы между модулями без необходимости.
6. Отделяй типы данных API от внутренней модели БД, когда их структуры различаются.
7. Для входящих HTTP-данных используй runtime-валидацию Zod. TypeScript не заменяет валидацию.
8. Не используй необоснованные приведения типов через `as`.
9. Для новых типов предпочитай вывод типов из Zod-схем, когда это уместно.

## 5. Правила React

1. Используй функциональные компоненты.
2. Не деструктурируй props непосредственно в параметрах функции.

   Правильно:

   ```tsx
   const FormCard = (props: FormCardProps) => {
   	const { title, status } = props
   }
   ```

3. Типы props выноси в `ComponentName.types.ts`.
4. Не экспортируй типы props через публичные `index.ts` UI-компонентов без необходимости.
5. Не добавляй локальные `focus-visible`, если глобальные стили уже обеспечивают нужное поведение.
6. Используй существующие компоненты, хуки и утилиты.
7. Не усложняй компоненты преждевременной оптимизацией.
8. Не храни производные данные в отдельном состоянии без необходимости.
9. Для асинхронных операций предусматривай loading, error и empty states.
10. Учитывай доступность: семантический HTML, label, keyboard navigation и корректные сообщения об ошибках.
11. Анимации используй сдержанно и только когда они улучшают UX. Если Framer Motion уже установлен, предпочитай его для сложных анимаций.

## 7. Архитектура backend

Предпочтительное разделение ответственности:

- `routes` — регистрация HTTP-маршрутов.
- `controllers` — HTTP-запросы и ответы.
- `services` — бизнес-логика.
- `repositories` — SQL-запросы.
- `schemas` — Zod-схемы.
- `db` — подключение к SQLite и миграции.
- `middleware` — общая обработка запросов и ошибок.

Правила:

1. Не размещай SQL непосредственно в контроллерах.
2. Не размещай бизнес-логику в маршрутах.
3. Контроллеры должны оставаться небольшими.
4. Используй единый формат ошибок API.
5. Обрабатывай ошибки централизованно.
6. Не раскрывай клиенту stack traces и внутренние детали сервера.
7. Используй корректные HTTP-методы и статус-коды.
8. Не доверяй входным данным, включая параметры URL и JSON-тело.
9. Не используй внешние API, обязательные секреты и удалённые базы данных.
10. Не добавляй авторизацию: по условиям задания административная панель доступна без неё.

## 8. SQLite

Предварительная модель данных:

- `forms` — формы.
- `pages` — страницы форм.
- `fields` — поля страниц.
- `submissions` — отправленные анкеты.
- `answers` — ответы на поля.

Общие свойства полей хранятся в отдельных столбцах, специфичные настройки — в `fields.config` как JSON.

Значения ответов хранятся в `answers.value` как JSON.

Правила:

1. Используй подготовленные SQL-запросы с параметрами.
2. Не формируй SQL конкатенацией непроверенных пользовательских значений.
3. Включай `PRAGMA foreign_keys = ON`.
4. Используй транзакции для операций, изменяющих несколько связанных таблиц.
5. Используй миграции для изменения схемы.
6. Не редактируй уже применённые миграции. Добавляй новые.
7. Не удаляй и не пересоздавай базу при обычном запуске приложения.
8. Не сохраняй реальные данные приложения в Git.
9. Проверяй внешние ключи, ограничения уникальности и целостность связей.
10. Не используй ORM без согласования.
11. Не полагайся только на `CHECK(json_valid(...))`: структура JSON должна проверяться через Zod.
12. Не изменяй структуру формы с уже полученными ответами без согласованной стратегии сохранения их целостности.

## 9. Валидация форм

Типы полей MVP:

- `text`
- `textarea`
- `email`
- `number`
- `radio`
- `checkbox`
- `select`

Правила:

1. Используй discriminated union по `type`.
2. У каждого типа поля должна быть собственная схема `config`.
3. Для вариантов выбора используй стабильные идентификаторы вариантов.
4. Проверяй `required`, ограничения длины, диапазоны и допустимые варианты.
5. При отправке ответов загружай актуальную схему формы из SQLite.
6. Никогда не доверяй схеме полей, присланной студентом.
7. Проверяй, что все переданные `fieldId` принадлежат отправляемой форме.
8. Не допускай повторяющихся ответов на одно поле в одной отправке.
9. Сохраняй отправку и её ответы атомарно, в одной транзакции.
10. Не сохраняй частично прошедшие валидацию отправки.

## 10. API

Предварительные маршруты:

### Административные

- `GET /api/forms`
- `POST /api/forms`
- `GET /api/forms/:id`
- `PATCH /api/forms/:id`
- `DELETE /api/forms/:id`
- `POST /api/forms/:id/publish`
- `GET /api/forms/:id/submissions`
- `GET /api/forms/:id/submissions/:submissionId`

### Публичные

- `GET /api/public/forms/:slug`
- `POST /api/public/forms/:slug/submissions`

Это предварительный контракт. Не изменяй его без обсуждения.

API возвращает JSON. Для неизвестных `/api/*` возвращай JSON-ошибку `404`, а не HTML frontend-приложения.

## 11. Запуск и сборка

Обязательные требования:

```bash
npm install
npm start
```

- Команды запускаются из корня репозитория.
- Приложение работает на `http://localhost:3000`.
- Поддерживается `process.env.PORT`.
- Не требуется отдельный сервер БД.
- Не требуются внешние сервисы и API-ключи.
- SQLite и необходимые таблицы создаются автоматически при первом запуске.
- Существующие данные сохраняются при повторном запуске.
- В production-режиме Express обслуживает собранный frontend.
- Прямое открытие React Router страниц должно работать.
- Не запускай Vite dev server как обязательный второй процесс при `npm start`.
